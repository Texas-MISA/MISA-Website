✅ **Stage 6 phase 8 shipped 2026-08-08** — **the merge tool**, from `/admin/members/[id]`. **No migration.**
  - 🔓 **The roadmap's central claim about this phase was WRONG, and correcting it is the design.** Both docs said a merge "can hit `attendance_one_per_event` when both identities attended the same event". It **cannot**: that index is keyed on `(event_id, normalized_eid)` — the *submitted* EID — and **not on `member_id`**, so repointing never touches an indexed column and the guard is structurally unreachable. The failure is therefore **silent** — two `present` rows for one event, and both views aggregate per row, so the points count twice and `events_attended` can exceed `events_possible`. The resolution is the doc's own (keep one, **reject** the other, which leaves the partial index *and* stops counting for points) but it is the application's job, not the database's.
  - 📌 **The hazard is asserted against real Postgres before the fix is asserted.** `tests/member-merge-actions.test.ts` opens by proving a naive repoint returns no error and double-counts; then that reject-first does not. If the claim had been wrong, everything else here would have been over-engineering.
  - ⚠️ **Only one of the three FKs to `members` fails loudly, and the dangerous one cascades.** `attendance` is `on delete set null` (silently orphans), `point_adjustments` is **`on delete cascade`** (silently destroys grants), `dues_payments` is `on delete restrict`. The Stage 6.5 note that the restrict makes a forgetful merge fail loudly is true *for dues* and false for the other two — so `commitMerge` **re-counts all three and refuses to delete unless every count is zero**.
  - ⚠️ **The merge is not atomic and cannot be** (no cross-statement transaction in PostgREST — the `writeAudit` gap). The order is chosen so every partial failure is **recoverable**: repointed-but-not-deleted is a visible duplicate holding no data, which the officer merges again. The irreversible step is last and is guarded.
  - **One `member.merged` row, on the SURVIVOR**, because the loser's row is deleted and there is no page for a member that does not exist — so that row is the only surviving record and carries the loser's name, EID, **id** and the counts in `note`. Each collision also writes its own `attendance.rejected`.
  - **Survivor wins the identity fields; only custom fields are chosen.** Notes are concatenated, never overwritten; `joined_at` takes the earlier of the two — which is why `AUDITED_MEMBER_COLUMNS` gained `joined_at` (a walkthrough finding: the merge wrote a column the trail did not record).
  - 🪤 **The suggestion ranker's calibration does not carry over, and the seed cannot supply a new one.** Between two members `email_exact` and `id_exact` are impossible (unique indexes), so the two +100 signals can never fire. The seeded roster yields **zero** member-vs-member pairs above 15 across all 496, so the floor was measured against **constructed** shapes: duplicates land at 65–110 on two axes, different-person shapes top out at 50. `MIN_DUPLICATE_SCORE` 60 **plus two agreeing axes**; "same name, nothing else" is deliberately not offered.

✅ **Stage 6 phase 6 shipped 2026-08-07** — **the relational filters**: attended / missed a specific event, has-pending, not-seen-since, and events-attended bounds. **No migration** — three of the four are plain columns on `member_directory`.
  - 🪤 **The event filter is a PostgREST embed, not a uuid list, and the rejected option's numbers are worth keeping.** Resolving attendees to ids and narrowing with `.in()` **414s at ~220 ids** (Kong's 8KB header buffer; measured 150→200 OK, 220→414), and §2.2's worst case is 150 attendees an event — a 1.4× margin that shrinks further because the id list shares the URL with the search term and the `cf:` filters. An officer could 414 by *adding a search term to an event filter*. Instead: one `attendance!left(event_id)` embed, with `attendance=not.is.null` for attended and `is.null` for missed. Measured: 15 + 17 = 32, so the two modes **partition** the roster and `count=exact` is right in both.
  - 🪤 **The embed lives in the SELECT, and the select literal cannot be built dynamically.** PostgREST types the row off the string *literal*, so concatenating widens it to `string` and collapses every field access — the `GenericStringError` break for the third time. Each caller holds **two `as const` literals and one branch**; `needsAttendanceEmbed` in `lib/filters.ts` owns the decision even though the literal cannot live there. ⚠️ The page and the export route must branch **identically** — an export that forgot the embed answers PGRST100 on exactly the filters that work on screen.
  - ⚠️ **`status = 'present'` on the embed is load-bearing.** A member whose check-in is still queued did not attend as far as credit goes; counting them as present would disagree with the leaderboard. A pending fixture lands in *missed*, and a test pins it.
  - ⚠️ **"Not seen since" includes members never seen at all.** `last_seen_at` is null for anyone never marked present, and a bare `.lt()` drops nulls silently — so "who has gone quiet?" would answer with the quietest members missing. It emits `or(last_seen_at.is.null,last_seen_at.lt.<instant>)`, Central-anchored.
  - 📌 **That is the SECOND `or` group on the query**, alongside the free-text search. Separate `or=` params **AND** together, which is what two independent concerns want — the failure the search's comment warns about is splitting *one* concern across several calls, and the two are easy to confuse.
  - 📌 **`FilterableQuery` gained `is` and `not` — not the `in`/`not`/`lt` the roadmap predicted.** That prediction assumed the uuid list. The recorder fake in `tests/filters.test.ts` stopped compiling the moment the interface widened, which is what the structural type is for.
  - ⚠️ **These are the first filters that narrow on data the directory does not display**, which cuts against the phase-3 trim. They live in an **Attendance filters** panel that says so in a sentence, and 🔓 **the panel opens whenever one of them is active** (`<details open={hasRelationalFilter(filter)}>`, not component state) — a collapsed panel hiding an applied filter is the phase-1 defect with a lid on it.

Three sharp edges in the Supabase CLI on this machine:

- **`db query` reads only the first line of its SQL argument.** Multi-line SQL silently truncates and fails with a confusing syntax error. Flatten to one line, and remember Windows caps a command line near 8k characters — `scripts/seed-remote.sh` exists to work around both.
- **`db query` targets the remote unless you pass `--local`, and `--linked=false` does NOT mean "not linked".** The flag is a boolean; the `=false` is discarded and it reads as `--linked`, so the query goes to production. The failure is quiet and convincing — a member id fetched "from local" 404s on a local page, a row count "proves" local drift — because both databases hold plausible data. **Verify which database answered before believing a surprising result**, using an id or a count you already know.

- **Newer stacks don't auto-grant table privileges to the API roles.** A fresh local stack gives anon/authenticated/service_role only `TRUNCATE/REFERENCES/TRIGGER` on new tables — every API read/write fails with 42501 no matter what RLS says. - **`db reset` does not re-read `config.toml`.** Container environment is baked at `supabase start`, so `db reset` replays migrations against containers still holding the old settings. A changed `jwt_expiry` (or any other `[auth]` value) needs a full `stop` + `start`. The symptom is a config change that appears to do nothing; confirm with `docker inspect supabase_auth_MISA-Website --format '{{range .Config.Env}}{{println .}}{{end}}' | grep GOTRUE_`.
- **`~/.supabase/profile` breaks every command that shells out to the legacy Go child.** A dangling active-profile pointer (a bare name, no extension) makes the child feed the path to viper, which fails with `failed to read profile: Unsupported Config Type ""` → `LegacyGoChildExitError`. `start` and `db query --linked` are unaffected, so it looks like a `db reset`-only fault. ## Architecture

Next.js App Router on Vercel → Supabase Postgres. No separate API service: Server Components read, Server Actions and Route Handlers write. Authorization lives in Postgres Row Level Security, not in the frontend (§2, §3).

Three audiences, one codebase:

| Audience | Auth |
|---|---|
| Public — org info, upcoming events | none |
| Members — check in, leaderboard, own history | none; identity-based (student ID + matching email), no accounts in v1 |
| Officers — schedule, roster, attendance review, points | Supabase Auth session + a matching `admin_profiles` row, enforced by `proxy.ts` |

Domain model: `members` ↔ `events` ↔ `attendance`, plus `point_adjustments`, `admin_profiles`, and one `admin_audit` log. Aggregates live in the `leaderboard` and `member_directory` views rather than in application code (§4). Routes are listed in §5.

## Invariants

These are decisions the architecture doc argues for at length. Don't quietly reverse one — if a change needs to, raise it and update the doc.

- **All writes go through Server Actions or Route Handlers.** The browser holds only the anon key, and RLS policies are written assuming the anon role is hostile. Never ship a client-side write; never expose the service role key to the client. The service-role client exists **only** in `lib/supabase/admin.ts`, guarded by `server-only`; anon-capable reads belong on `lib/supabase/server.ts` so RLS stays exercised. (§3, §6)
- **The duplicate rule is three checks, not one** (v1.18): the `(event_id, normalized_student_id)` partial unique index (23505), an app check on `(event_id, member_id)` after member resolution (same member via two raw IDs), and an app check for a prior pending orphan within the grace window (the index ignores `event_id is null`). A pending orphan never blocks a new event-resolved submission; rejected rows never block re-entry.
- **`ORPHAN_WINDOW_HOURS` lives in `lib/checkin.ts` and is always passed explicitly** to `nearby_events()`; the SQL `default 48` is for ad-hoc SQL only. (§9 #7)
- **Nothing that resolves to a known member is ever dropped on the floor.** A check-in from someone the roster recognizes is always stored — as `pending` if it matches no open event, for an officer to resolve. A member who showed up and got no credit is the failure mode that erodes trust in the whole system. (§4.2)
  - **The member half is narrower, and deliberately so** (2026-07-31). A submission matching no roster member whose submitter did *not* tick "first time" is **discarded rather than stored** — re-prompted instead, however many times it fails. The alternative was silently creating a duplicate member for every double typo, and duplicates have no merge tool (see the Stage 6 notes). Accepted cost: someone who never gets their details right leaves no trace at all. The recovery path is officer manual entry at `/admin/attendance/new`, already reachable from the ADD A CHECK-IN button in the `/admin/attendance` header — **what changed is the trigger, not the page**: an unrecognized submission used to leave a queue row an officer would find unprompted, and now the only signal is a member saying the form won't take their details. Full spec, decision table, and the accepted membership-oracle tradeoff: [`docs/attend-confirmation-flow.md`](docs/attend-confirmation-flow.md).
  - Corollary: `unmatched` must mean "definitely not on the roster", never "we couldn't tell". A member lookup returns a discriminated `found`/`missing`/`error`, because reporting a transient database fault as a re-prompt would turn a whole room away with no attendance and no trace — the exact outcome this invariant exists to prevent.
- **Creating a member is not part of check-in resolution.** `resolveCheckin` looks members up; only the confirmed second pass (`declaredNew && confirmed`) may create one, and `createMember` in `lib/checkin.ts` is the single place in the application that inserts a `members` row on an unauthenticated request. The confirmation is a guard against honest typos, **not a security control** — a scripted POST carrying `step=confirm` creates a member in one request, which is correct, since the server re-derives everything rather than trusting the previewed payload. The per-IP throttle is the abuse control.
- **The first-time checkbox is a hint, not an instruction.** Ticking it when you already exist links you to yourself; it must never create a second person. The lookup (ID, then email) always runs first, and `existing` on `needs_confirmation` carries a bare boolean — never the matched member's name, email, or ID, which would turn §6's accepted "is this ID on the roster" oracle into "here is the human behind it".
- **`present_requires_resolution` is load-bearing.** `status = 'present'` guarantees both `event_id` and `member_id` are non-null, so leaderboard queries can trust the status alone. Never work around it in application code. (§4.1)
- **Match and dedupe on the normalized generated column, never the raw submitted value.** (§4.2)
  - **Applied 2026-08-02 (migration 16).** The columns are `members.normalized_eid` and `attendance.normalized_eid`, generated from `eid` / `submitted_eid`, and the identifier is a real UT EID (alphanumeric, `abc1234`) rather than `UT` + six sequential digits.
  - **What the normalization buys changed with it.** The old worked example (`ut-12345`, `UT 12345`, `UT12345` are one person) exercised whitespace and hyphen stripping, which EIDs never contain. What it buys now is case-insensitivity, and **the fold is to `lower`, not `upper`** — EIDs are conventionally lowercase and the review screen otherwise shouts `ABC1234` back at someone who typed `abc1234`. The stripping stays in the expression: harmless, still catches pasted junk, and removing it would rewrite every stored value for no gain.
  - **The ranker's calibration did not survive the format change.** `id_contains` (+35) was **removed** — it existed solely to catch a dropped `UT` prefix, and against short alphanumerics `includes` degrades into a substring match that clears the floor alone. Distance 2 stays below `MIN_SUGGESTION_SCORE` and distance 1 still stands alone.
  - 🪤 **The reason the floor is still needed is not the reason it was written.** Sequential six-digit IDs put ~3 members within distance 2 of *any* number. EIDs are not sequential — but they are derived from name initials, so the near-miss population is **correlated with the roster** instead, which is the same problem from the other direction and arguably worse: a one-character typo now lands on a real *and plausibly confusable* person more often. `seed.sql` reproduces the cluster deliberately (`mp8570`, `pn8571`, `ro8574` all sit at distance 2 from Rowan Pike's `rp8571`) and `tests/seed-fixtures.test.ts` asserts that row still renders no suggestions.
- **Every officer mutation writes an `admin_audit` row** — actor, timestamp, before/after JSON, reason. One audit table keyed `(entity_type, entity_id)`; do not add per-entity audit tables. Append-only: no client role may update or delete a row. (§4.2, §6)
- **Authorization lives in `lib/auth.ts`, not in `proxy.ts`.** Proxy refreshes the session and does an optimistic redirect only — no database query, because it runs on prefetches. Every admin page and layout calls `requireOfficer()`; every admin Server Action starts with `getOfficer()` and returns `{status:"unauthorized"}`. Actions must not call `requireOfficer()`: `redirect()` throws `NEXT_REDIRECT`, and the house try/catch would swallow it. For the same reason **every `redirect()` goes outside the try/catch**. (§5, doc v1.19)
- **`app/actions/audit.ts` must never gain a `"use server"` directive.** Every export of such a module is a public endpoint, and a client-callable `writeAudit(actorId, …)` would let anyone forge audit rows under any officer's name. It is a plain `server-only` module.
- **Carry `updated_at` as the raw PostgREST string.** It has microsecond precision; a JS `Date` round trip truncates to milliseconds, and the edit compare-and-set then never matches, reporting a phantom conflict on every save. This covers `attendance` as well as `events` — both carry the column and the same trigger.
- **Single-row attendance mutations compare-and-set on `updated_at`; bulk operations scope on `status = 'pending'` instead** and report requested-minus-updated as skipped. Status-scoping alone would not catch two officers assigning *different* events to a row that stays pending, and catches nothing at all for a field edit or a note — but carrying 200 `updated_at` strings through a form buys nothing.
- **A point adjustment is never updated except to void it, and never deleted.** No edit UI, no `updated_at`, no CAS token: voiding is a one-way transition, so `.is("voided_at", null)` on the UPDATE is already a complete guard, and zero rows back means someone voided it first. The asymmetry with `attendance` is deliberate. (§4.2)
- **A near-miss EID needs corroboration at edit distance 2; distance 1 stands alone.** A bare distance-2 match is a coincidence, and it used to offer three confident-looking strangers for a submission from someone on no roster at all. Distance 2 scores below `MIN_SUGGESTION_SCORE` and must be joined by a second reason. An empty suggestion list is a valid answer — that is the point of the floor, not a gap in it.
  - The original reason was that *sequentially issued six-digit IDs* put ~3 members within two edits of any number. That reason expired with the EID switch and the rule survives on a different one — see the amendment under "match and dedupe" above. Don't relax the floor on the grounds that EIDs are not sequential.
- **Officer attribution distinguishes "no display name" from "no profile".** `fetchOfficerNames` returns `Map<string, string | null>`: absent means the `admin_profiles` row is gone (revoked), null means a current officer who never set a name. Collapsing the two credited every ordinary officer to "a former officer" in the one log that exists to say who did what (§6). Readers must handle all three cases.
- **Suggestions are ranked by the database and never reordered in JavaScript**, and nothing is ever preselected. `nearby_events()` is the authority on proximity, `ORPHAN_WINDOW_HOURS` is always passed explicitly, and the app only annotates. Suggestion lists render with nothing checked, and the member ranker returns an empty list rather than a weak guess — this is "don't auto-resolve near-misses" carried into the UI, where a stray `defaultChecked` is the easiest way to break it by accident.
- **A cap that silently truncates is a correctness bug waiting on growth, and this codebase has two.** `MEMBER_SCAN_LIMIT` (400) bounds the roster scan under every member picker and the near-miss ranker — past it, members simply are not offered, with no error and (in `attendance/[id]`, which does not order) no determinism either. `RATE_LIMIT_MAX` (90 per IP / 10 min) is a *room* capacity, since a venue's WiFi is one IP, and it refuses real attendees once the room outgrows it. Both were sized against the org as it is now and both are documented at their definitions. Never raise one without re-reading why the number was chosen, and never add a new cap that fails quietly — refuse loudly or page, don't trim. (§2.2's capacity check, doc v1.31; open items in `tasks.md` under Capacity ceilings.)
- **Bulk actions operate on explicitly checked IDs only, and report partial success** rather than failing wholesale — **for actions over rows that already exist.** Pulled forward from Stage 6 because Stage 5 introduces the first bulk action, which is when the mistake gets made. The pre-flight must dedupe *within* the selection too — two selected rows can be the same person.
  - **A multi-member grant is the exception, and inverts the rule: one atomic insert, all-or-nothing** (`grantPoints`, phase 4). Partial success is right for `bulkAssignEvent` because a skipped submission stays visibly in the queue for someone to notice. A partial grant has no such backstop — eleven of twelve members credited, the officer told it worked, and the twelfth finds out a month later. So a bad member id costs the whole grant and the officer keeps every pick to retry with. Corollary: an oversized selection must be **refused, never truncated** to the cap, which is the same bug wearing a different hat.
- **One filter object, one translation, and the row window outside it.** `applyMemberFilter` in `lib/filters.ts` is the only thing that turns a `MemberFilter` into a query, and it deliberately never applies a `.range()` or a `.limit()` — the window is the caller's. This is structural, not a matter of care: "copy all N matching this filter" has to be provably the same query as the count rendered beside it, and the classic way this screen breaks is a second hand-written query drifting out of step and silently returning a subset. Any new filter goes in that one function, never in the page.
  - ⚠️ **The directory stopped paginating on 2026-08-07** — it renders every member matching the filter — but the separation is *more* load-bearing now, not less. **Both callers read in chunks of `READ_CHUNK` (1000)**: the hosted project applies its own PostgREST `max_rows`, so one unbounded request comes back complete locally and silently short in production. `pageRange`/`pageCount`/`PAGE_SIZE` are gone; `chunkRange()` replaced them. If a `.range()` ever migrates *into* `applyMemberFilter`, every caller inherits it and the export starts returning one chunk and reporting success — `tests/filters.test.ts` asserts it never does.
  - **There is deliberately no ceiling on the directory.** The count and the rows are always the same set, so they cannot disagree; a cap would re-introduce a partial list that looks complete, which is the thing this whole screen exists to prevent. §2.2's worst case is 500 members — one chunk. If it ever gets slow, virtualize the table; do not start trimming the result.
  - **A filter with no control on screen is the same defect wearing a different hat.** Phase 3 therefore *removed* the six retired fields from `MemberFilter` rather than hiding their controls: an old bookmark carrying `minRate=50` now narrows nothing, instead of narrowing invisibly and leaving the officer a count they cannot account for. Retiring a filter means deleting the field; `parseMemberFilter` reads by key and is total, so ignoring the stale param is free.
    - **`page` left the same way** when pagination went (2026-08-07), and for the same reason rather than out of tidiness: a bookmarked `?page=3` must narrow nothing, not silently offset a list whose control no longer exists. Verified in a browser — `/admin/members?page=3` renders the complete roster.
- **A free-text search value is sanitized where the filter is built, and quoted where it is used.** `parseMemberFilter` strips the ILIKE wildcards (`%`, `*`) and the two characters a quoted PostgREST value cannot survive (`"`, `\`), so anything holding a `MemberFilter` holds a query-safe string and no caller needs a second escape pass. `.` and `,` are deliberately kept and handled by **double-quoting the value** inside the `or` group — stripping them would make every email unsearchable, and an unquoted `email.ilike.*a.person@example.edu*` is parsed as a malformed operator rather than as a search. A pure test cannot catch that; `tests/member-directory.test.ts` asserts it against real PostgREST.
- 🔓 **A custom-field key is interpolated into an `order=` term *and* (since phase 5c) into a `cf:` filter predicate, so its format check is a security control, not a naming convention.** A directory sort or filter on an officer-defined field becomes `custom_fields->>key`, and PostgREST parses whatever comes out. The phase-4 spike (2026-08-02) measured what an unconstrained key buys: a key containing `,` **breaks out of the order term and is read as a second order column** — `custom_fields->>a,b` came back `42703 column … b does not exist`, meaning an arbitrary column name would have been accepted. `.` and `)` fail as PGRST100 parse errors, but a **space and a `"` were accepted silently, with no error at all**, so "PostgREST rejected it when I tried" is not a boundary. `FIELD_KEY_PATTERN` (`^[a-z][a-z0-9_]{0,39}$`) in `lib/members.ts` is the escape, enforced three times on purpose: the zod schema, `member_field_definitions_key_format` in migration 18, and again in **`customFieldColumn()`** — the one *function* through which a key becomes part of a query string, and therefore the one that must re-check rather than trust its caller. It serves both call sites deliberately: a second copy written for filters would be a second thing to get wrong, which is why phase 5c renamed it off `customSortColumn`. Ordering by a hidden column leaks no values; that is not a reason to leave the door open.
  - **The sort key is namespaced `cf:<key>`, and that is a different guard for a different problem.** It stops an officer-defined field from shadowing a built-in sort (`MEMBER_SORTS` is a closed list of four; a field keyed `email` would otherwise win). `:` cannot appear in a key at all, so the split is unambiguous both ways. The namespace is **not** what makes the key safe — only the pattern is.
  - **`applyMemberFilter` takes the definition list as a *required* argument while `parseMemberFilter` defaults it to none.** The asymmetry is the point: a page that forgets to load definitions is a compile error at the query, rather than a directory that silently sorts by name. A `cf:` key naming an archived field, or one not shown in the directory, falls back to `name` — sorting by a column nobody can see is the same defect the phase-3 trim removed.
- **A list read in more than one request needs a total order, not merely a sort.** Rows tied on the sort column can come back arranged differently per request, so the reads skip and repeat rows — and it reads as missing data rather than as an ordering fault. Every directory query ends `.order("id")`. The seeded roster is 32 members and cannot show this: fixtures have to exceed the read window deliberately.
  - ⚠️ **This survived pagination's removal unchanged**, because chunked reading has exactly the same hazard as paging — it is the same `.range()` boundary with a different name. `tests/member-directory.test.ts` uses a local `CHUNK = 7` rather than `READ_CHUNK` (1000), since proving the property against 1000 would need a thousand fixtures and the property does not care about the size.
  - **Custom-field sorts make this the common case rather than the edge case.** A dropdown has a handful of options across the whole roster, so almost every row is tied. The spike reproduced the failure directly: 30 rows read at 7 came back as 30 rows but 29 distinct — one duplicated, one never shown. `tests/member-directory.test.ts` pins it against real PostgREST, on its own `t3qcf` fixtures rather than the file's shared `t3q` ones, because earlier blocks add members as they run.
- 🔓 **Nothing in the database ties a stored custom-field value to its definition's option list, and that is deliberate.** The column check is `jsonb_typeof = 'object'` and no more; `setMemberFieldValue` plus `isAllowedFieldValue` are the *only* enforcement anywhere. Editing an option list therefore **orphans** every member holding a value that just left it — rewriting their answers to match would falsify what the roster said, and refusing the edit would make a typo'd option permanent. The consequence is a rendering obligation: a `<select>` whose value matches no `<option>` shows **blank** in every browser, so the member would appear to hold nothing and the officer's next edit would destroy a real answer that was never displayed. `fieldOptions()` in `lib/members.ts` appends the orphan as a trailing disabled entry — visible, clearable, not re-appliable. Never "fix" this with a trigger validating `custom_fields` against the definitions; the coupling is not worth it at this size, and the orphan is information.
- **A member's compare-and-set token is row-level, so the *row* owns it, not the cell.** `members.updated_at` is one value that every inline cell and the notes editor posts back. If each form held its own copy from the server, the first save would move it and strand every sibling on a stale token — the officer's second edit in that row reports a phantom conflict, and their third, until a revalidation lands. `directory-row.tsx` and `member-editor.tsx` hold the token in state and adopt the fresh one each save returns; that is why the row is the Client Component and `member-table.tsx` is not. The failure is a client-side timing window that no behavioural test in this suite would catch, so `tests/members.test.ts` pins the boundary as a source assertion instead.
  - Corollary, and the reason the view carries `updated_at` at all: both editing screens **read `member_directory`** and compare against `members`. Migration 18 appends the column so the render side has a token without a second read.
- **A custom-field value is stored by deleting the key, never by writing `""`.** `setFieldValue` in `lib/members.ts` returns the whole next object — PostgREST has no partial jsonb update, and the audit before/after wants both complete objects anyway — and clearing a dropdown removes the key. An empty string would make "cleared" and "never answered" two states that render identically and sort differently, which is the null-vs-zero rule (`attendance_rate`) arriving in a new place. `fieldValue` collapses missing and empty to `null` so no caller decides for itself.
- **`attendance_rate` is null, not zero, when the term has no completed events**, and a member who attended nothing is a real `0`. Render null as "—" (`formatAttendanceRate` in `lib/members.ts`); a threshold filter correctly excludes it, because "no rate" is not "meets the threshold". Collapsing the two sorts an unrated member below a real 5% at the start of every semester.
- **A member's events grid has three states, not two: attended, missed, and _upcoming_.** `events_possible` counts only published events with `ends_at < now()`, so an event that has not happened yet is not a miss — painting it as one contradicts the rate printed above it and makes every member look worse at the start of a term. `classifyTermEvents` in `lib/members.ts` owns this, takes `now` as an argument, and uses the same half-open boundary the view does. Attendance outranks the clock: a present row on an event that has not ended is attended.
  - **The grid and the view's counts can legitimately disagree, and neither is derived from the other.** `member_directory` counts present rows against any non-cancelled current-term event, *drafts included*; the grid is published-only. The view is the authority on the numbers, the grid is the per-event breakdown, and `tests/member-directory.test.ts` pins that attended + missed equals `events_possible`.
- **Dues status is calculated, never ticked** (Stage 6.5; the schema and the core are built as of phase 1, doc v1.38, spec `docs/dues-and-membership.md`). "Official member" means a non-voided `dues_payments` row whose `covered_terms` includes `current_term()`, surfaced as the single boolean `member_directory.dues_paid_current_term` and rendered **Paid / Not Paid**. It gates nothing (§9 #12): check-in, points, and the leaderboard are untouched, which is the reversible choice — a gate later is application logic over a column that already exists.
  - 🔓 **The dedupe key is Venmo's transaction ID, and a content fingerprint is not an acceptable substitute.** Officers upload overlapping statements deliberately, so de-duplication is the normal path rather than an edge case. Two members can send $30 in the same minute with the note `"dues"`; a fingerprint over `(datetime, amount, payer, note)` collapses them and the second member is unpaid with no trace anywhere in the system. The unique index **spans voided rows**, so re-importing a statement whose payment an officer already voided stays a no-op instead of resurrecting it.
  - **Nothing that arrived as money is dropped on the floor** — §4.2's rule extended, and stronger here than for attendance: somebody sent real money and holds a receipt the system does not. An odd amount, an unreadable note, a note naming two members, no note at all — the row is stored and queued. **A payment note never creates a member**, exactly as check-in resolution never does, and matching is **exact-match only**; the queue may offer ranked suggestions (reuse `scoreMemberCandidates`, don't grow a second ranker) with nothing preselected.
  - **The review axis is a nullable `terms_covered`, not a status enum.** Null means "no officer has decided how many terms this bought", so an amount matching neither configured price parses, links, and waits. `covered_terms` is generated from it, so an undecided row covers nothing — the failure direction is *under*-reporting membership, which the queue makes visible, rather than over-reporting it, which nothing would.
  - **`dues_payments.member_id` is `on delete restrict`, diverging from `point_adjustments`' cascade on purpose.** The row records that money arrived; losing it because a member row went away is the wrong trade, and it makes the phase-8 merge tool fail loudly if it forgets to repoint dues alongside attendance and points.
  - **A payment is editable *and* voidable — the union of the two patterns already here.** Editable (CAS on `updated_at`) because the parser can attribute a payment wrongly and correcting that is legitimate; voidable-with-reason rather than deletable because money arriving is a fact. `point_adjustments` is voidable but not editable, `attendance` is editable but not voidable; this is deliberately both.
  - **Prices live in `app_settings` in cents and are read at import time only.** `terms_covered` is stored on the row, so raising dues never rewrites what last year's payments bought.
  - 🪤 **Terms do not sort lexicographically.** `'Fall 2026' < 'Spring 2026'` is true as a string compare and false as a calendar fact. Every "which term is later" question goes through the **term index** — `term_index()` in SQL, `termIndex` / `isLaterTerm` in `lib/dues.ts` — and never through `max(term)` or `order by term`. Same class of error as `new Date("2026-09-01T18:00")`: plausible output, wrong answer, no error anywhere. This is why there is no "paid through" column on the view.
    - The index is two terms a year with Spring first (`Spring 2026 → 4052`, `Fall 2026 → 4053`), so ordering is integer comparison and stepping is addition. Chosen over iterating `next_term` because `covered_terms` is a **generated column**, which requires an immutable expression — and because a total order is what the trap actually needs, not just a successor function.
  - ⚠️ **`dues`, `dues_paid`, and `dues_paid_current_term` are reserved custom-field keys**, in migration 19's CHECK and in `RESERVED_FIELD_KEYS`, which move in the same commit. Without them an officer recreates the hand-ticked dropdown beside the calculated column and the roster carries two answers to one question. Reserving `dues` alone is not enough — `dues_paid` is the name people reach for, and it is the key phase 4's own walkthrough created (✅ that fixture was deleted from the local database 2026-08-05). 📌 The generalisable part: **archiving a definition does not free its key.** Migration 18's unique key index spans archived rows on purpose, so any migration that forbids a key must reckon with archived definitions holding it, not just live ones.
  - **The import is a Server Action, not a Route Handler**, and it re-parses server-side rather than trusting the preview. A Server Action takes a `File` in `FormData`; the Route Handler rule here is about *downloads* needing `Content-Disposition`. The CSV text is held in the browser between the preview and commit steps — 🔓 **never persist the uploaded file**, which is every dues transaction for a month in one blob.
- **A roster export is audited as its own receipt.** `admin_audit.entity_id` is `uuid not null` and an export spans N members, so each export generates a uuid nothing else references, under entity type `'roster'`, with the filter and row count in `after`/`note`. Don't make `entity_id` nullable to avoid this, and don't borrow a member's id — the row would read as an action taken against that one person. (§6 requires every export logged; it is the largest PII egress point in the system.)
  - **Since doc v1.30 the receipt also carries the chosen field list and the format**, because the export is a *field picker* over CSV and `.xlsx`, not the displayed columns. Once columns are a choice, the filter alone no longer answers what left the building.
  - ⚠️ **It records the fields that actually left, not the ones that were ticked** (`exportedFields` in `lib/export.ts`, phase 5a). The clipboard's `emails` and `names` formats emit one column each regardless of the picker, and logging four for an email copy answers §6's question with a superset — erring wide is still erring, and a receipt that over-reports is one nobody can reason from a year later. Found in the phase-5a walkthrough, and the fix lives in the pure core rather than the route because it is a decision, the same reason `planBulkAssign` is not inside `bulkAssignEvent`.
  - **The clipboard is audited exactly like the download.** Copying every matching email is the same egress as saving a file; only `Content-Disposition` differs, which is why both go through the one Route Handler.
- 🔓 **A CSV cell beginning `=`, `+`, `-`, or `@` executes as a formula when an officer opens the file, and member names are attacker-supplied** — anyone who can check in during an open window picks their own (§6). Escaped in `lib/export.ts`'s CSV writer by prefixing `'`; the victim is the officer's machine, not the server. Tab and CR are guarded too, because Excel strips leading whitespace before deciding. The `.xlsx` path is *not* exposed, since its cells are written as typed values — which is why the two writers must not share a "join it with commas" shortcut, and why xlsx must never be implemented as CSV with a different extension.
  - ⚠️ **The xlsx writer has no formula guard, and its absence is asserted.** An xlsx cell carries its type and is never re-parsed, so copying the CSV apostrophe there would corrupt a legitimate name for no gain. The two writers share `projectRow` and nothing else.
  - 🪤 **A hand-rolled workbook fails as Excel's "we found a problem with some content" repair prompt — one symptom for every cause.** Four things produce it and all four are pinned in `tests/xlsx.test.ts`: fills 0 and 1 must be exactly `none` then `gray125`; `numFmts` must be the first child of `<styleSheet>` with the rest in schema order; every `count` attribute must equal its real child count (derive them, never write literals); and a custom `numFmtId` must be ≥ 164. Two more of the same shape: `<autoFilter>` goes **after** `<sheetData>`, and illegal C0 control characters must be stripped from text — officer notes are free text, and one of them makes Excel reject the whole package rather than the cell.
  - 📌 **Two things look wrong in Excel's ribbon and are not** (confirmed on a real open, 2026-08-06). A number cell reports its type as **`General`** — that is what a plain number *is* in Excel; the cells carry no format on purpose, and the tell that it is numeric rather than text is that Excel right-aligns it and sorts it without a conversion step. A date cell reports **`Custom`** rather than `Date`, because `yyyy-mm-dd` is not one of Excel's built-in *named* formats; the cell is still a real serial with no `t` attribute. **The ISO format stays** rather than built-in `numFmtId` 14 (`mm-dd-yy`): ISO is unambiguous across locales, survives a paste elsewhere, sorts chronologically even as text, and matches what the CSV writer emits so the two formats cannot disagree.
  - ⚠️ **The Excel date epoch is `1899-12-30`.** Excel keeps a February 29, 1900 that never existed, inherited from Lotus 1-2-3; that base absorbs both the phantom day and the 1-based count. The serial is taken from the **Central** civil date (`exportDate`), not a UTC slice — otherwise every evening signup lands a day late, which is the `new Date("2026-09-01T18:00")` class of bug in a new place.
  - ⚠️ **The guard fires on text cells and must never fire on numbers.** `bonus_points` is legitimately negative, and `'-5` stops being a number the moment it lands in the sheet. This is the whole reason `ExportCell` is a typed union rather than `string[][]` — a "escape everything" pass over stringified rows would be correct for names and wrong for every negative number. Both directions are pinned in `tests/export.test.ts`, and the guarded-name case was confirmed end to end in a browser against a real row (phase 5a walkthrough).
- **Selection is two modes, not one set that happens to be full.** `selection.tsx` holds either explicit `ids` or `filter`, and in `filter` mode the export sends **no ids at all** so the route re-runs the same filtered query — which is what makes "all N" provably all N rather than whatever happened to be rendered. Explicit ids **narrow** that query rather than replacing it, so a stale checkbox cannot pull in a row the filter excludes. Selection resets on a filter change and deliberately **not** on paging: the reset key is the filter params with `page` deleted, and that same string is the export's query string.
- **A file download is a Route Handler, and it opens with `getOfficer()` returning 403.** `requireOfficer()`'s `redirect()` would answer a download request with a login page. This is the mirror of the Server Action rule for a different reason — actions avoid `requireOfficer()` because the house try/catch swallows `NEXT_REDIRECT`; a route handler avoids it because a 302 is the wrong answer to `fetch`ing a spreadsheet. A Server Action cannot set `Content-Disposition` at all, which is why the download is a route in the first place.
  - ⚠️ **A Route Handler does not participate in layouts**, confirmed against the shipped Next 16 docs — so `app/admin/(shell)/layout.tsx`'s `requireOfficer()` never runs for one. Living inside the `(shell)` group is colocation and grants **no** protection. `proxy.ts`'s `/admin/:path*` matcher does cover the path and 307s an unauthenticated request to login before the handler runs, but that is a convenience: the `getOfficer()` 403 is what catches a signed-in user with no `admin_profiles` row, and what survives a matcher change. Both are required; neither substitutes for the other.
  - **An export pages through explicitly and never calls `pageRange()`.** Chunks of 1000, because the hosted project applies its own `max_rows` that local does not — an export complete in development can come back short in production, which is the partial-list failure wearing a different hat. `MAX_EXPORT_ROWS` (5000) **refuses; it never truncates**, and it sits far under Vercel's 4.5 MB non-streaming response limit.
  - **An id that reaches a PostgREST `in.(…)` list is format-checked first**, the same discipline `FIELD_KEY_PATTERN` applies to a sort key. Anything not a uuid is dropped before the query is built.
- **A saved view stores the canonical query string, and it is canonicalised on WRITE against every definition that exists.** Two halves, and the second is not obvious. The first: a preset is a name over what `memberFilterToParams` emits, never a jsonb copy of `MemberFilter` — one representation of that type, and a string that is a function of the filter rather than of click order, which is what makes "which preset is active?" a string comparison. The second: **a rename is a write**, and the manage form posts the row's stored query straight back, so canonicalising it against the *live* field definitions re-derives a filter the officer never touched and drops any `cf:` clause whose field is currently archived or hidden. `storableFields` over `includeArchived: true` closes it. **Storage is permissive; application stays strict** — the directory parses with live, in-directory definitions, so an archived field narrows nothing while archived and works again if restored. Never canonicalise on read.
- 🔓 **`attendance_one_per_event` cannot catch a merge, so the application must.** The index is `(event_id, normalized_eid)` — the *submitted* EID — not `(event_id, member_id)`, so repointing `member_id` never touches an indexed column. Two identities have different EIDs by construction, which means merging them gives the survivor two `present` rows for one event, and both `leaderboard` and `member_directory` aggregate per row: the event's points count twice and `events_attended` can exceed `events_possible`. **Nothing errors.** The merge detects the collision itself and **rejects** the losing row — a rejected row leaves the partial index *and* stops counting for points, so the double count is prevented rather than reported. Never "simplify" a merge into three UPDATEs.
- **Repointing a member's rows and deleting the old row are ordered, and the order is a safety property.** Exactly three tables reference `members(id)`, and only one fails loudly: `attendance` is `on delete set null` (silently orphans check-ins), `point_adjustments` is **`on delete cascade`** (silently destroys grants), `dues_payments` is `on delete restrict`. So a delete that runs before the repoints is unrecoverable for two of the three, and the restrict is not the safety net Stage 6.5's note implies. `commitMerge` **re-counts all three and refuses to delete unless every count is zero**.
  - ⚠️ **It is not atomic and cannot be** — PostgREST has no cross-statement transaction, the same gap `writeAudit` records. The order is therefore chosen so every partial failure leaves a *recoverable* state: repointed-but-not-deleted is a visible duplicate holding no data, which the officer merges again. The one irreversible step is last and is guarded.
- **A roster import creates only, and duplicate detection covers BOTH unique indexes.** `members` carries `members_normalized_eid` *and* `members_email_lower`; an importer checking one shows a clean preview and then takes a 23505 on the other. A row matching an existing member is counted, shown and never written — a stale spreadsheet must not overwrite a correction an officer made, and create-only is what makes re-importing a no-op. The pre-flight also checks the file against **itself** on both axes, which is the "dedupe within the selection too" rule applied to a file naming one person twice.
  - 🪤 **The write is one atomic insert, deliberately NOT the upsert the dues import uses.** PostgREST's `onConflict` takes a single target, so an upsert cannot express "skip if either index matches" — and unlike dues, a roster is not *designed for* overlapping re-imports. All-or-nothing is right for the `grantPoints` reason (a partial import reported as success has no backstop) and is safe to retry because the preview recomputes: anything already written comes back as `existing`.
  - **An import's column list is `exportCatalogue`'s importable subset**, so the export's labels are the import's headers and a file can round-trip. Calculated columns are ignored *and named* in the preview. Columns are located **by name, never by position**.
- **A wrapped PostgREST column list is a build break, not a style choice.** This has now bitten twice, in `lib/points.ts` and again in the directory page. PostgREST types the returned row off the string *literal*, so `"a, b" + "c"` widens to plain `string` and collapses the result to `GenericStringError` — the symptom is every field access failing at once, which reads as a schema problem. One unbroken literal with `as const`, every time. Assume it once per screen that selects more than a handful of columns.
- **Both sides of an audit before/after must select the same columns.** `AuditTrail` diffs the union of their keys and renders a key present on one side only as `—`, so a narrower `.select()` on the update *invents changes that never happened*: voiding a point adjustment logged `reason: "Staffed the info booth" → —` and `awarded_by: <uuid> → —`, as though the void had erased both. `AUDITED_ADJUSTMENT_COLUMNS` in `lib/points.ts` is the shared list — one unbroken string literal with `as const`, because PostgREST types the returned row off the literal and a concatenation widens to `string`.
- **`admin_audit.action` is a closed union in TypeScript and free text in SQL; readers must tolerate unknown values.** Two pre-Stage-5 rows on the production database carry the bare verbs `reject` and `void` and are permanently uncorrectable — the append-only trigger raises P0001 on `UPDATE` and `DELETE` alike. Format with a fallback to the raw string.
- **Date-range filters are Central-anchored and half-open:** `.gte(centralWallTimeToInstant(from, "00:00"))` … `.lt(centralWallTimeToInstant(addCivilDays(to, 1), "00:00"))`. A bare `.lte("submitted_at", "2026-04-07")` is a UTC-midnight cut that silently drops five to six hours of a Central day — the same class of bug as `new Date("2026-09-01T18:00")`, and it fails plausibly.
- **Server Components own date formatting.** `Intl.DateTimeFormat` inside a Client Component runs on both sides of hydration, and Node and Chrome ship different ICU data for the space before "PM". The resulting React diff shows two strings that look character-for-character identical. Pass formatted labels down as props.
- **React 19 resets an uncontrolled `<form action={…}>` once the action resolves.** Any form that re-renders with server state (validation errors, the §4.6 confirmation, `/attend`'s re-prompt) must echo the submitted values back in that state and drive every `defaultValue` from them — otherwise the officer's edits silently revert, a confirmation saves the old values, and the check-in re-prompt clears the fields the member is trying to correct. The same reset clears checkboxes, so **any selection state mirrored outside the form must be reset alongside it** — the bulk bar read "2 selected" above six empty boxes until it was.
  - Pass a **string, never `undefined`**. A nullish `defaultValue` following a non-nullish one makes React drop the `value` attribute, and the reset then clears the field — so `state.submitted?.x ?? ""`, never `state.submitted?.x`. No `key` remount is needed: the mutation phase writes the new attribute before `form.reset()` reads it.
  - **Never put `formAction` on a submit button whose `name`/`value` you read.** React drops the submitter's name from the FormData when it carries `formAction`, so the field arrives pre-hydration and vanishes after — a bug that only shows up on a slow phone. And **one carrier per field name**: React inserts the submitter's name/value immediately before the submitter, so a hidden input of the same name earlier in the form wins `formData.get()`.
- **A control's enabled state comes from the live form, not from the server's copy of the row.** Deriving "can this be approved?" from the fetched record meant picking an event left APPROVE disabled until a save round-tripped, turning one officer intent into two writes. Server state is the authority on what *is*; the form is the authority on what the officer is *about to do*.
- **Never build a timestamp with `new Date("2026-09-01T18:00")`.** The server runs in UTC. Wall-clock times go through `centralWallTimeToInstant()` in `lib/events.ts`, which iterates civil dates and attaches the zone last — the only thing that keeps a weekly 6pm meeting at 6pm across the November DST change.
- **Point adjustments require a `reason`, are voided rather than deleted, and may be negative.** A void is itself a recorded action with its own reason. (§4.2)
- **The public `leaderboard` shows a single `total_points`; `member_directory` keeps `attendance_points` and `bonus_points` split.** This asymmetry is deliberate (§4.4) — the officer-facing directory and the `/admin/points` ledger are where discretionary grants stay visible, since the public board no longer reveals them. Don't "fix" the inconsistency by collapsing the directory columns too.
- **Both views are scoped to `current_term()`.** Any new aggregate must use the same scope, denominators included — an all-time `events_possible` against a current-term `events_attended` understates every rate and still looks plausible. (§4.4, §4.5)
- **A view has no RLS, so the blanket grants do not protect it. Every non-public view must explicitly `revoke all … from anon`, and every recreate must re-issue that revoke.** `20260730000012_api_role_grants.sql` grants `all privileges on all tables in schema public` to anon and argues it is safe because "RLS is the security boundary". That is true for tables and **false for views** — `grant all on all tables` includes views, and `member_directory` deliberately runs as owner (`security_invoker` off) so it can aggregate *past* the deny-all tables underneath. Found in production 2026-08-02: the anon key could read every member's student ID and email, breaking the "no unauthenticated route returns an email or student ID" invariant three sections below. Fixed in migration 15.
  - **Why it survived review:** `members` itself denies correctly, RLS is on, and there are no policies — so every check aimed at the table came back clean. Checking the table proves nothing about a view over it.
  - **The recreate trap:** the same migration sets `alter default privileges … grant all on tables`, so a newly *created* view inherits anon access. `create or replace` does not re-trigger this; `drop` + `create` does. Any migration that recreates a view reopens the hole unless it re-revokes.
  - `tests/security.test.ts` enumerates every view the migrations declare and asserts anon can select from none but `leaderboard`, which is public by design and carries neither identifier. Adding a name to that allowlist is a privacy decision, not a maintenance chore.
- **Change a view with `create or replace`, which can only *append* columns — never reorder, rename, retype, or drop one.** Dropping the view drops its grants with it, and `member_directory` is granted to `authenticated` as a §6 security boundary. This is why `attendance_rate` sits last in migration 14 rather than beside the counts it derives from.
  - **The one exception, added 2026-08-01: renaming an output column requires a drop.** `create or replace` cannot do it, and Stage 6 phase 2 renames `student_id` → `eid`. A drop is permitted *provided the same migration re-issues* `grant select on public.member_directory to authenticated`. DDL is transactional, so there is no window where the grant is missing — the real hazard is a migration that forgets the re-grant, which fails at the next read rather than at migration time, and only for non-service-role callers. Say why in the migration header whenever you take this path.
- **Never type a term string.** `events.term` is generated from `starts_at` via `term_of()`, and `current_term()` derives from `now()` unless an officer has pinned `app_settings.current_term`. A literal `'Fall 2026'` anywhere in application code is a bug. (§4.7)
  - **`seed.sql` is application code for this purpose**, and it broke the rule until 2026-08-06: `point_adjustments.term` was the literal `'Spring 2026'`, which silently stopped matching the moment the seeded dates moved. It is now `term_of(<the award date>)` — derived, and coherent whenever the seed is run. Omitting the column is *not* the fix: it defaults to `current_term()`, which is the term the seed is **run** in rather than the term the grant belongs to.
  - 🪤 **The seed no longer pins `current_term` at all** (2026-08-06), because its data now lives in the term the clock is in. That closes a real divergence — `tests/global-setup.ts` un-pins for the suite, so the local database and the test run used to disagree about what `current_term()` was. **The cost lands on 1 January 2027**: the pin was what stopped seeded data falling out of scope at a term boundary, so on that date the leaderboard and directory go empty with nothing on screen to say why. That is `seed.sql` needing its dates moved forward, not a bug.
- **No unauthenticated route returns an email or student ID** — including the `leaderboard` view, which deliberately omits both. (§4.4, §6)
- **`/leaderboard` is public but must never be indexed.** It carries `robots: { index: false, follow: false }` (the pattern is already in `app/admin/(shell)/layout.tsx`). Names against point totals are the residual exposure once IDs and emails are gone, and a search cache outlives the deploy that filled it — this is the one privacy choice here that cannot be undone by shipping a fix. (§9 #1)
- **Event edits are not retroactive.** Recorded attendance is a fact; the check-in window is consulted only at resolution time. Narrowing a window warns, it never revokes. Deleting an event that has attendance is blocked — offer `status = 'cancelled'` instead. Changing `points` is allowed but must warn with the count of members affected. (§4.6)
- **Check-ins outside the 48-hour orphan grace window are refused, not queued.** Inside it with no open event, they're stored `pending` with ranked `nearby_events()` suggestions. (§4.3)
- **Don't auto-resolve near-misses.** A submission five minutes past the window is probably legitimate, but auto-approving it just moves the boundary. Keep the human in the loop and make the human's job fast instead. (§7, Stage 5)
- **"Select all N matching this filter" is not "select the rows you can see."** Conflating them silently produces partial email lists — the classic bug in this kind of screen. (§7, Stage 6)
  - ⚠️ **The two now pick the same people on screen and must still not be merged** (2026-08-07). With no pagination every matching row is visible, so ticking the header covers the whole result — but `ids` mode exports exactly what was ticked while `filter` mode re-runs the query, and only the second can prove a list is complete rather than merely long.
  - 🔓 **Keeping them apart also fixed a failure removing pagination would otherwise have introduced.** The header checkbox used to enumerate 25 ids; unpaginated it would enumerate every one, and the export appends one `ids=` param per member. Measured in the walkthrough: **28 members already makes a 1,257-character URL**, so a 500-member roster would overrun request-header limits and the download would simply fail. The header checkbox therefore sets `filter` mode, which sends **zero** ids — confirmed live at 29 members, 0 `ids` params, a 109-character URL.
- **The database must stay disposable.** Every schema change is a file in `supabase/migrations/` — never applied only through the dashboard SQL editor. The whole handoff/transfer story (§2.3) rests on `create project → link → db push` recreating the database from the repo alone; drift between the live schema and `migrations/` breaks it silently. (§2.3)
- **Check-in window bounds are half-open (`>= opens`, `< closes`) in three places that must agree:** the `events_no_overlapping_checkin` exclusion constraint, `open_event_at()`, and any application-side window logic. Making one inclusive either blocks back-to-back events from being published or lets one instant match two events. (§4.3)
- **RLS is enabled on every table, deny-all until Stage 8** — with one deliberate exception: `events_public_read` grants anon `select` on `status = 'published'` events (the §6 grant, pulled forward for the Stage 2 landing page). New tables must ship deny-all in their own migration. All other reads reach clients only through `leaderboard` and `member_directory`, which run as owner and are the security boundary; writes are deny-all everywhere. (§4.4, §6)
- **`seed.sql` must not use trailing inline comments.** `scripts/seed-remote.sh` flattens each chunk onto one line, so a `--` after code would comment out everything following it. Full-line comments are stripped and safe.
  - 🪤 **"Stripped and safe" was not true for a comment containing an emoji, and it half-seeded production on 2026-08-07.** The stripper was `sed 's/^[[:space:]]*--.*$//'`, and in a UTF-8 locale GNU sed's `.*` fails to match a line holding a multibyte character — so the comment survived, got flattened into the SQL, and reached the CLI as a flag (`Unrecognized flag: -- 🪤 …`). The wipe and the members chunk had already applied, so the remote sat at 32 members and no events until it was re-run. **Fixed in the script** with `grep -v -E '^[[:space:]]*--'`, which anchors on the marker and never has to match the rest of the line, so emoji in seed comments are fine now. The generalisable part: a comment stripper that can silently *not* strip turns a comment into executable input, and the error it produces names anything but the real cause.
- 🔓 **Re-seeding a project that has a real officer on it needs `--force`, and that is the only sanctioned way.** `seed.sql`'s guard refuses whenever `auth.users` holds a non-seed account, which is true of every project anyone has signed into, so the guard blocks the ordinary case forever after the first login. `--force` skips the guard chunk and nothing else: it still wipes everything the seed wipes, it names the linked project ref and prints the current row counts **before** deleting, and it requires the operator to type the ref back. Officer logins are not deleted. Never get past the guard by editing a copy of `seed.sql` instead.
- **The seeded semester must sit in the term the clock is in, and its completed events must be in the past.** Two constraints decide every date in `seed.sql`: `term_of` bounds the term, and attendance can only hang off events with `starts_at < now()` — an event in the future carrying attendance would push somebody's `attendance_rate` above 1, or divide by zero. Moving the seed to Fall 2026 on 2026-08-06 therefore **compressed twelve completed events into 1–5 August**, the only elapsed days of the term. That is deliberate, documented at the events block, and should be spread back out once more of the term has elapsed. 🪤 Its visible side effect: with twelve events inside five days every orphan falls within the 48-hour grace window of *several*, so `nearby_events()` returns a ranked list where it used to return one obvious answer.
