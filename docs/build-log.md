✅ **CHECK-IN LOCATION VERIFICATION BUILT — migration 28 (2026-08-22).** Requested 2026-08-19, replanned against four officer decisions, built the same day. Spec: [`checkin-location-verification.md`](checkin-location-verification.md). One table, one column, **no new route** — a pill on the event's attendance list and a checkbox on the event form.

  - ✅ **The blocking question from the 2026-08-19 plan is closed, and it went the good way.** That plan called the forwarded-for header *"a blocking question for the feature, not a detail"* — if `x-forwarded-for`'s client-controlled end were spoofable, anyone reading this public repo could defeat the check. Vercel's own documentation settles it: it **overwrites** the header and **does not forward external IPs**, expressly to prevent spoofing, and overriding it needs the Enterprise Trusted Proxy add-on. `clientIp()` prefers `x-vercel-forwarded-for` anyway — identical value, but the one a proxy in front of Vercel could not overwrite. ⚠️ **That makes the header unforgeable, not the check unevadable.** Joining the venue wifi still defeats it completely.
  - 🔓 **The toggle gates DERIVATION, not COLLECTION, and that asymmetry is the whole feature.** `events.verify_origin` defaults true and is flippable long after an event; origins are captured on every check-in regardless. That is what makes "turn it on next week and the flags appear" work with no backfill — and it is why `/attend` now carries a disclosure sentence written in the **unconditional present tense**. Hedging it with "we may", or describing the toggle, would document the wrong thing.
  - ⚠️ **Cellular is never flagged**, on the officer's call. It removes the largest false-positive class — real attendees whose phone had not joined the wifi — and it is a **documented public bypass**: turn off wifi and the check cannot see you. Correct only while nothing gates on the flag. ✂️ §6's rotating per-event venue code was **dropped** in the same decision rather than built alongside; the two overlapped enough that both was redundant.

  **Three things that were only learnable by measuring, and each changed the design:**

  - 🪤 **The carrier table cannot be hand-written, which the approved plan assumed it could.** It said "a few dozen prefixes". Measured against RIPEstat: **AT&T Mobility (AS20057) announces 1,633 IPv4 prefixes, Verizon's Cellco (AS6167) 3,842, T-Mobile (AS21928) 538** — ~6,300 against UT's 8. A wrong `cellular` entry is worse than a missing one, because it hands a free pass to whoever is inside it on the strength of a fabricated fact. So the table is **generated and committed** (`scripts/build-network-table.mjs`), which the plan had named only as the eventual maintenance answer. 📌 Merging overlapping announcements collapses 6,302 prefixes to **137 v4 + 32 v6 ranges in a 7KB file** — the artifact is an order of magnitude smaller than the estimate that made hand-writing look attractive. Every property the officer picked the approach for survives: **no runtime dependency, no request-time network call, no member's address leaving the server.**
  - 🔓 **UT ANNOUNCES NO IPv6, and taking that seriously changed the classifier's contract.** AS18 is eight IPv4 prefixes and nothing else, so `CAMPUS_V6` is empty — and a student on campus wifi over IPv6 would match no campus range **not because they are off campus, but because there is nothing to match against**. Calling that `other` would flag a member sitting in the room, which is the single failure this feature is least allowed to have. So `classifyNetwork` returns `other` **only when matching nothing actually means something**: if a family's campus table is empty, the answer is `unknown`, which is never flagged and carries no digest. Self-correcting — the moment UT's v6 space is found and added, IPv6 classifies normally. 📌 **The generalisable bit: "matched nothing" and "we have nothing to match with" are different answers, and a lookup table that cannot tell them apart will state the first while meaning the second.**
  - 🔓 **`network_type = 'unknown'` implies `origin_hash is null`, and it is a CHECK constraint rather than a convention.** The review screen classifies in precedence order and its last rule is *"matched no venue, not campus, not cellular → off-network, flagged"*. An unclassifiable address carrying a digest falls straight through to it and is reported as evidence against a member **on the strength of a parse failure**. `checkin_origin_unknown_has_no_digest` makes the refusal a property of the database, exactly as `present_requires_resolution` does. ⚠️ Not an equivalence — a pending orphan legitimately has a real kind and a null digest, because there is no `event_id` to hash with.

  **Two defects found in existing code, one fixed and one deliberately not:**

  - 🐛 **`tests/security.test.ts`'s generic write sweep was passing on this table for the wrong reason.** Every probe filters on `id`; this table's primary key is `attendance_id`, so the DELETE probe came back **42703** ("column does not exist"), which satisfies `error !== null` while proving nothing about permissions. Same family as the empty-payload trap the file already warns about. Verified by hand with the correct column — the real answer is **42501** — and a targeted probe added that asserts it. 📌 The readability half needed its own fixture too: `seed.sql` writes no origin rows, so "anon cannot read this" would have been asserted against a table with nothing in it.
  - 🐛 **`saveEvent`'s audit `before` selects 14 columns and its `after` selects 8** — the exact shape the "both sides must select the same columns" invariant exists to prevent, where a narrower `after` invents changes that never happened. `verify_origin` was added to **both**, so this feature is symmetric; the underlying asymmetry predates it and was **left alone** rather than changed as a side effect of an unrelated build.

  🪤 **A migration edited after being applied needs a `db reset`, and the test that caught it was the one asserting the constraint.** The `unknown`-has-no-digest CHECK was added to migration 28 after the first reset, so the local database did not have it and the insert it should have refused succeeded. Loud, immediate, and only because the constraint had a test — the sibling assertions all passed. Safe to fix by editing the file because nothing was pushed: *the database must stay disposable* is what makes that true.

  ✅ **The headline requirement is proved end to end, not just asserted.** Three cases in `tests/checkin-origin-capture.test.ts` build an event with the toggle **off**, run eight real check-ins through the capture path, confirm all eight origins were recorded **anyway**, and confirm every row derives `off` — then flip the flag after the event is over and watch the same eight stored rows establish a venue and produce `at_venue: 6, on_campus: 1, off_network: 1`, with the row count still **8**. Nothing is written or backfilled to make that happen. A second case flips it back off and confirms the evidence survives, so it is a view toggle and not a delete; a third confirms the default is on and that turning one event off leaves another alone. 📌 Written because *is it toggleable, and can it be toggled afterwards* is exactly the kind of requirement that is easy to assert and easy to have subtly wrong.

  📌 **Two things deliberately NOT done, flagged rather than skipped quietly:** the pill is **not** on the `/admin/attendance` queue (its rows are overwhelmingly `pending`, which carry no digest by construction, and a per-event mode would have to be computed across a filtered list spanning events); and the two thresholds — `VENUE_MIN_COUNT` 5, `VENUE_MIN_SHARE` 0.5 — are **unmeasured room judgements** to revisit after one real event. Retention is also still open (§9 #15).

  ⚠️ **Worth measuring before trusting the "elsewhere on campus" state at all:** open `whatismyipaddress.com` on UT wifi in two different buildings. If the university NATs campus-wide that state can never fire, and the feature reduces to "not on UT's network" — which the CIDR test alone already answers. It **cannot** be measured after the fact, because `event_id` is inside the hash precisely so digests cannot be compared across events.

  🔍 **REVIEWED 2026-08-22, same day, and the review found six defects in it.** Recorded because five were in code that had already passed 1,098 tests, lint, `tsc` and a clean build — the suite was green and the feature was wrong in five places.

  - 🐛 **IPv4-mapped addresses were folded by REGEX, so only the canonical spelling worked.** `::ffff:128.83.140.7` folded to its v4 meaning; the equally valid uncompressed `0:0:0:0:0:ffff:128.83.140.7` did not — it fell through to the IPv6 branch, landed in an empty `CAMPUS_V6`, and produced a **v6 digest for a v4 client**. One client, two digests, silently dropped out of its own venue mode. Now tested on the parsed value (`v6 >> 32n === 0xffffn`), which the regex version could never have covered. 📌 **The generalisable bit: structure covers every spelling; a regex covers the one you thought of.**
  - 🐛 **The origin insert relied on the CALLER's try/catch, which is not fail-open.** It runs after the attendance row is written, so a rejection — as opposed to a returned `{ error }` — escaped into `submitCheckin`'s house try/catch and returned `error` to a member **whose check-in had already succeeded**. They would retry and be told they were a duplicate. PostgREST failures normally arrive as `{ error }`, which is exactly why the rejection path is the one that ships unnoticed: the returned-error case is the one anybody writes a test for. ⚠️ **The new test was checked against the unfixed code and does fail without it** — a regression test that passes both ways proves nothing.
  - 🐛 **Officer-entered rows were badged "Origin unknown".** Capture never runs for `admin_manual` — correctly, since those rows carry the officer's own origin — so every walk-in an officer typed in fell through to `unknown`. That badge claims the system tried to determine an origin and failed; the truth is the concept does not apply to the row. Now a distinct `not_applicable` that renders nothing, ordered **above** the missing-record check because that is what makes it reachable.
  - 🐛 **The review screen read origins with an `.in()` list of every attendance id.** One uuid is ~37 characters, and §2.2's worst case is 150 attendees — a **5.5KB query string on a GET**, which is the same shape as the 1,257-character URL that made the member picker abandon id enumeration at 28 members. Now filtered by event through the embedded attendance row, so the URL is a constant length however large the event gets.
  - 🐛 **Window membership compared ISO strings, and was correct only by ASCII coincidence.** PostgREST renders `submitted_at` with microseconds (`…23:12:32.506781+00:00`) and a whole-second `starts_at` without any (`…23:00:00+00:00`), so the comparison was between two different shapes — landing on the right answer only because `.` (0x2E) sorts after `+` (0x2B). Nothing declared that, and a non-UTC offset would have broken it silently. Extracted to `withinCheckinWindow`, which parses, and is pinned by tests carrying both real shapes plus an offset-notation case.
  - 🐛 **A nested `<label>`.** The checkbox was wrapped in the file's local `Field`, which renders a `<label>` of its own — invalid HTML with undefined click-target behaviour — and its required `label` prop rendered an empty `<span>` above the control. A checkbox is its own label; the wrapper is gone.

  **Three findings reported and deliberately NOT changed**, because each is either pre-existing or costs more than it buys:

  - ⚠️ **`ORIGIN_CAPTURE_ENABLED` was declared and never used**, which meant a missing `CHECKIN_ORIGIN_PEPPER` in production would have been **completely silent** — every event would simply have read "not enough check-ins came from one network" forever. Now wired into the event page's summary line, which names the variable. *(This one was fixed; it is listed here because the defect was an absence rather than a mistake.)*
  - 📌 **anon can read `events.verify_origin`** through `events_public_read`, so anyone can query the public API for which events are unchecked. **Left alone deliberately:** cellular is a blanket bypass on every event regardless, and the whole mechanism is documented in a public repo, so this reveals nothing an attacker needs. Closing it means revoking the table-level `select` and re-granting column by column, which is fiddly machinery that the next migration adding a column would silently get wrong.
  - 📌 **`event-form.tsx` still defines its own local `Field`**, twelve call sites, despite `components/ui/field.tsx` existing — a survivor of exactly the drift the 2026-08-17 rework was meant to end (it found *nine* copies of this component). Not touched here: it is unrelated to this feature and would be a twelve-site edit riding in on a security change.
  - 📌 **The origins read is unbounded**, against the standing rule that a hosted project's `max_rows` silently shortens one big request. Consistent with the attendance read on the same page, which is also unbounded, and both cap at the same number — so they stay in step. Realistic event size is ~150. Worth chunking the day either one is chunked.

🎠 **The home page marquee was never seamless, and was fixed 2026-08-14 (doc v1.60).** Reported as "it stops or moves left to right interchangeably, and has a noticeable end". **No migration, two files.**

Measured on production at a 1646px viewport: the top track's group is **1360px** (5 x 260 + 5 x 12) and the bottom's **1272px** (6 x 200 + 6 x 12), so at the end of a cycle each track had translated a full group width and its right edge sat **286px** and **374px** short of the viewport — bare navy, then a snap back.

The tracks span the full width, so a mouse resting anywhere over the band froze that row. The check that finds it is numeric and takes one call: pause the animation at points across a full cycle (negative `animation-delay` + `animationPlayState: paused`) and assert the track's right edge is never left of `window.innerWidth`.
